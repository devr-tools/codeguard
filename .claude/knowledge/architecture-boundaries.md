# Architecture & System Boundaries

Key architectural decisions, service boundaries, data flow, integration points, and why things are the way they are.

- **Repository config is an untrusted input.** codeguard runs in CI on PRs, so `codeguard.yaml`/rule packs are attacker-controllable. Command execution and non-allowlisted AI provider base URLs are gated behind `internal/codeguard/trust` (a process-global `Policy`), off by default. The trust anchor is env vars / CLI flags (`--allow-config-commands`, `--allow-config-ai-endpoints`), never config. See `docs/security.md`.
- **All config-derived command execution must go through `trust.GuardConfigCommand`** before `exec`. Existing chokepoints: `runner/support/commands.go:runCommandCheck`, `ai/runtime/provider.go` (command provider), `ai/nlrule/runtime.go`, `ai/semantic/runtime.go`, and `runner/govulncheck/govulncheck.go:Run` (gates a config-supplied `security_rules.govulncheck_command` override; the built-in default binary `govulncheck` resolved from PATH stays ungated so default "auto" mode works). codeguard's *own* fixed tool invocations (git, the built-in `node -e` TS runner) are NOT gated — only commands (or command names) sourced from config. **NOTE:** the govulncheck override was historically an RCE hole — it exec'd the config value with no gate and defaulted on for Go targets; do not remove the guard.
- **Outbound AI HTTP must use `internal/codeguard/ai/safehttp`**: `ValidateProviderURL` (allowlist of public hosts unless opted in) + `Client` (blocks loopback/private/link-local at dial time) + `MaxResponseBytes`. Triage (`ai/triage`) and the runtime providers (`ai/runtime`) both route through it. Triage merges env-then-config base URL; only the env-sourced value is treated as trusted (`BaseURLFromEnv`).
- **OWASP categories are baked into the rule catalog at var-init time**, not via `init()`. The merged `catalog` var calls `withSecurityOWASP(mergeRuleCatalogs(...))` in `rules/catalog.go`; an `init()` would run *after* the `catalog` var initializer copied stale entries. The mapping lives in `rules/catalog_security_owasp.go`. All read paths (`Catalog`, `RuleCatalogForConfig`, SARIF, CLI) flow through `rules.Catalog()`.
- Config-controlled artifact paths (`baseline.path`, `cache.path`, `ai.cache.path`) are resolved relative to the config dir and contained within it by `config.containConfigArtifactPaths` (in `config/io.go`, `LoadFile`). Paths escaping the config directory are rejected.
- The language-agnostic OWASP-gap line rules (CORS, debug, bind-all, weak-hash/cipher, deserialization, Dockerfile root) live in `checks/security/security_owasp_extra.go` and run per-line via `findingsForFile`. NOTE: `findingsForFile` is the **non-TypeScript** path — `securityTargetFindings` routes TS/JS targets to a separate `typeScriptTargetFindings` pipeline, so these rules do not run on TS/JS targets. String-literal signals (CORS, bind-all) match the raw line; call/identifier signals match the masked line.
- **Secret/credential scanning (`checks/security/security_secrets.go`) runs as its own repository-wide pass in `securityTargetFindings`, unconditionally for BOTH the TS and non-TS branches** — precisely so it covers TS/JS targets that bypass `findingsForFile`. Tiers: `security.hardcoded-credential` (fail; known provider formats + `security_rules.secrets.custom_patterns`), `security.private-key` (fail), `security.hardcoded-secret` (warn; lower-confidence name-based heuristic — was fail before, deliberately downgraded). Patterns match the **raw** line (the token lives in a string literal that masking would blank). Placeholder/allowlist filtering is done in Go after the regex match because RE2 has no lookahead (mirrors `isInsecureDeserialization`). Config: `security_rules.secrets` (`enabled`/`allow_paths`/`allow_patterns`/`custom_patterns`), defaulted in `applySecurityDefaults`, validated in `validateSecretsRules`.
- **PERF: the secret scanner is gated by a cheap literal pre-check (`builtinGatePasses`), not a combined regex.** Profiling showed `strings.Contains`/byte scans are ~85x faster than RE2 alternation, and that a leading `\b` or `(?i)` defeats RE2's literal-prefix fast path (those patterns ran ~1.8–7ms per 2000 lines; literal-prefix patterns like the Slack webhook ran ~50µs). The gate is `gateLiterals` (case-sensitive `strings.Contains`) + `gateFoldLiterals` (lowercase, via alloc-free `asciiContainsFold`); when a line contains no marker, the ~17 built-in regexes are skipped. Net: default scan went 3.2→99 MB/s, entropy mode 3.1→47 MB/s. **INVARIANT: the gate must be a superset of every built-in pattern — adding a credential pattern requires adding its required literal to the gate.** **This invariant was asserted here but NOT actually enforced: `TestBuiltinGateCoversPatterns` did not exist anywhere in the tree until it was written in Oct 2026** — verified by grepping every branch, where the only hit was this file. It exists now, in `security_secret_patterns_test.go`, and is generated rather than hand-maintained: it parses each pattern with `regexp/syntax` and enumerates concrete accepted strings (every alternation branch, every member of a small character class, 0/1 of optionals, min and min+1 of bounded repeats), then requires every variant the regex matches to pass the gate. The same generator backs `TestSecurityGatedPatternsAreSupersets` for the per-line gates. Two generator subtleties: `regexp/syntax` **factors** `(?:ghp|gho|ghu|ghs|ghr)` into `gh[oprsu]`, so branches hide inside character classes and small classes must be fully expanded; and a class representative must prefer a word character, since picking `-` out of `[0-9A-Za-z_-]` ends the sample on a non-word byte and defeats a trailing `\b`, which silently un-tested six credential patterns until fixed. Custom config patterns have arbitrary markers so they bypass the gate and always run.
- **CodeQL `go/regex/missing-regexp-anchor` (High) fires on unanchored regexes containing a host literal (e.g. `hooks\.slack\.com`), even for detection patterns.** The repo's accepted fix (see `quality_ai_style_drift.go:17` and the Slack webhook pattern in `security_secret_patterns.go`) is to bound the host with `(?:^|[^A-Za-z0-9_])(...)(?:$|[^A-Za-z0-9_])` — start/non-host-char on both sides — which adds the capture group as the matched value. CodeQL accepts this form; a bare `\b` or `(?:^|...)` left-only boundary may not. Apply this whenever adding a regex with an embedded domain literal.
- **HARDENING (codeguard scans untrusted PR content): the scanner bounds its work** — skips files > `maxScanFileBytes` (5 MiB in the secrets/line scanner), scans only the first `maxScanLineBytes` (64 KiB) of any line, and skips binary files (`looksBinary` = NUL byte in first 8 KiB). Separately, the shared per-scan file corpus (`runner/support/utils.go:WalkFiles` + `corpus.go`) skips files above its own `maxScanFileBytes` (32 MiB) at walk time and reads via `readCappedFile` (LimitReader) — this is the cap that stops a single multi-GB file from OOMing the in-memory corpus; the two constants share a name but live in different packages. The git-history parser uses `bufio.Reader.ReadString` (grows for any line length), NOT `bufio.Scanner` — Scanner silently stops on an over-long token, which for a security scan would skip the rest of history undetected.
- **The secret scanner exposes a pure API for reuse: `security.BuildScanner(cfg) Scanner` + `Scanner.ScanContent(content) []Match` + `Scanner.SkipPath(file)`.** `secretFindingsForFile` wraps `ScanContent` with `env.NewFinding`. Tiers in `scanLine` (one match per line, priority order): private-key → `credentialPatterns` (known formats + DB/Bearer/Azure, fail) → config `custom_patterns` → name-based (warn) → opt-in entropy (`security.high-entropy-string`, warn). Values are masked in messages via `maskSecret` (first4…last4). Entropy = `shannonEntropy` (bits/char) over whitespace-free quoted literals, gated by `secrets.entropy` (off by default; min_length 20, threshold 4.5). GitHub-token CRC32 checksum validation was deliberately NOT added — getting the algorithm slightly wrong yields false negatives (worse than a false positive for a security tool).
- **Git-history secret scan lives in its own top-level package `internal/codeguard/history` (shells `git log -p -U0`), exposed via `pkg/codeguard.ScanGitHistory` and the `scan-history` CLI command.** It MUST be a separate package, not `runner/support`: `checks/security` imports `runner/support` (for `MatchPattern`), so `runner/support` importing `checks/security` would cycle. `history` imports `checks/security` (above it) and is consumed by `pkg` + CLI (both top-level). The parser tracks `+++ b/<path>`, hunk headers (`@@ … +c`), and `+`/`-` line prefixes to attribute added lines to commits; dedupes by rule+path+masked-message keeping the newest commit (log is newest-first).
- **GOTCHA: `support.ScanTargetFiles` caches per-file findings keyed by `(sectionID, target.Path, rel)`.** If two passes scan the same files with the same `sectionID`, the second pass gets a cache hit and returns the FIRST pass's findings. The secret pass therefore uses a distinct cache id `"security-secrets"` (not `"security"`) so it doesn't collide with the language pass. `sectionID` here only affects the cache key — findings still land in the real section via their RuleID/`FinalizeSection`. When adding any additional `ScanTargetFiles` call to an existing section, give it a unique cache id.
- **GOTCHA: `ScanTargetFiles`'s per-file cache only works for PURE evaluators** (evaluators whose sole output is the returned `[]core.Finding`). On a cache hit the evaluator is NOT called, so any evaluator that builds state via a captured closure and returns `nil` will silently produce nothing once a warm cache exists. Clone detection hit exactly this (all `quality.duplicate-code` findings vanished on the second scan). Cross-file/stateful passes MUST use `VisitTargetFiles` (bypasses the findings cache, visits every file) instead of `ScanTargetFiles`. See `checks/quality/quality_clone.go:cloneDocumentsForTarget`.
- **PERF: the scan is parallelized at the section level** (`runner/checks/checks.go:Build`) on a `runtime.NumCPU()`-bounded worker pool; results are written into position-indexed slots so output order stays deterministic. This required making the shared mutable state concurrency-safe: `ScanCache` (mutex in `cache_types.go`), `ArtifactStore` (mutex in `artifacts.go`), and the per-scan file corpus. `OnSectionComplete` is wrapped in a mutex (`withSynchronizedSectionCallback`) since sections now finish concurrently. **CORRECTION (verified): file-level parallelism IS now used.** `ScanTargetFiles` passes `parallel: true` (`runner/support/findings_scan.go:32`, `maxFileScanWorkers = 4`); the serial behaviour evaluators that mutate closure state depend on now lives in the separate `ScanTargetFilesSequential`. So ANY shared mutable state reached from a `ScanTargetFiles` evaluator needs its own lock — a new rule consulting `goModuleResolver`'s go.mod cache hit `fatal error: concurrent map writes`, and it did not reproduce until the third scan run, so a couple of green runs is not evidence of safety.
- **PERF: files are walked, read, and Go-parsed once per scan via a shared `fileCorpus`** (`runner/support/corpus.go`), held by pointer on the by-value `Context` so all sections share it. `ScanTargetFiles`/`VisitTargetFiles` read bytes through it; `support.ParseGoSource(env, file, data)` returns a shared `*ast.File`/`*token.FileSet` (parsed with `ParseComments`) so quality and design no longer re-parse the same file. Cached ASTs are read-only — never mutate them. Tradeoff: peak memory is higher (the corpus retains all read bytes + ASTs for the scan), but wall-clock improves ~1.2x (small repos) to ~1.7x (large repos). Taint/graph/perf parsers keep their own cheaper parse modes (`SkipObjectResolution`/`ImportsOnly`) and are intentionally not routed through the shared cache.
- **The per-file cache fingerprint is per-config-family, not global** (`SectionConfigHashes` in `cache_helpers.go`; cache version bumped to 7). Each family (`quality`/`design`/`security`/`prompts`/`ci`/`contracts`) hashes only the config that can change its findings (quality also hashes `DesignRules` + `AI`; the rule catalog is in every family since a metadata override changes `NewFinding` output). `sectionConfigFamily` maps a cache section id to its family by prefix; unknown ids fall back to the `""` all-checks hash so a new section can never silently serve stale entries. Editing an unrelated field (output format, target names, exclude list) no longer invalidates the whole cache.
- **The MCP server is hand-rolled (no SDK) and transport-agnostic.** Shared JSON-RPC message builders + the synchronous method router live in `internal/cli/mcp_dispatch.go` (`buildResultMessage`/`buildErrorMessage`/`buildProgressMessage`, `serverCapabilities`, `dispatchSyncMethod`). Both transports reuse them. stdio (`mcp_run.go`/`mcp_requests.go`) keeps an async goroutine + cancel-map for `tools/call` (cancellation via `notifications/cancelled`); HTTP (`mcp_http.go`) runs `tools/call` synchronously per-request and streams progress over SSE, cancellation driven by the request context. When adding a capability, wire it into `dispatchSyncMethod` (HTTP picks it up automatically) AND the stdio method switch in `mcp_run.go`.
- **MCP server→client requests (sampling/roots)** flow through `internal/cli/mcp_client.go`: `clientCaller`/`clientBridge` + a `serverRequester` (pending-id→chan registry). The transport supplies a `send` closure and feeds inbound responses (classified by `isResponseMessage`: id present, no method) back via `serverRequester.deliver`. stdio demuxes responses in the read loop (`mcp_run.go handleLine`); HTTP needs the client to open the `GET {mcp-path}` SSE stream — server-initiated requests are written there and answered on later POSTs, correlated per session in `internal/cli/mcp_http_session.go`. Client capabilities are captured at `initialize` (`parseClientCapabilities`). The `clientCaller`/progress emitter reach tools via context (`withClientCaller`/`withProgress`), not signatures.
- **MCP fix tools** (`internal/cli/mcp_fix.go`): `verify_fix` wraps `service.VerifyFix` (caller diff); `propose_fix` wraps `service.GenerateVerifiedFix` with a generator resolved as sampling-first (`samplingGenerator` calls the client LLM) then `internalfix.NewAIGenerator(cfg.AI)`; `apply_fix` verifies then writes the tree via `runnersupport.ApplyUnifiedDiff` (the one `destructiveHint` tool), confirming via `clientCaller.elicit` (`elicitation/create`) when supported. Verification test execution is trust-gated, so it needs `CODEGUARD_ALLOW_CONFIG_COMMANDS=1` or it fails closed. Fix failures return `toolErrorResultData` (isError + structuredContent with attempted diff + remaining findings).
- **MCP `config_path` confinement**: caller-supplied `config_path` is confined (`confinePath` in `mcp_tools.go`) to the server config dir + cwd + client roots; the server's own `--config` default is never confined. This closed a remote arbitrary-file-read finding. Streaming: `core.ScanOptions.OnSectionComplete` (tagged `json:"-"` — marshaling a non-nil func errors) fires in `runner/support.FinalizeSection`.
- **`codeguard serve --mcp --http`** serves Streamable HTTP for remote hosts (Devin): `POST {mcp-path}` returns `application/json` for sync methods and `text/event-stream` for `tools/call`; optional static-bearer auth (`--auth-token`/`$CODEGUARD_MCP_AUTH_TOKEN`, constant-time compared), `GET /healthz`, body/concurrency caps, SIGINT/SIGTERM graceful shutdown. No OAuth. MCP resources (`codeguard://rules`, `codeguard://config`, `codeguard://rules/{rule_id}`) and prompts (`review-diff`, `triage-findings`, `explain-rule`) wrap the same SDK accessors the tools use. Devin onboarding pack: `examples/hooks/devin/`.
- The taint engine emits a single rule ID per language, chosen by sink: `goTaintRuleID`/`pyTaintRuleID` return `security.ssrf.{go,python}` when the sink is an outbound-HTTP callee (`goHTTPSinkArgIndex`/`pyHTTPSinkArgIndex`), else the generic `security.taint.{go,python}`. To add an SSRF sink, add it to the arg-index map; the rule routing and OWASP A10 mapping follow automatically.
- **Section dispatch is data-driven, not a hardcoded ladder.** `runner/checks/Build` iterates `sectionRegistry` (`runner/checks/registry.go`) — a `[]sectionDef{id, name, enabled(sc), run(ctx, sc, checkEnv)}`. To add a check section, append a `sectionDef`; do NOT reintroduce an `if cfg.X {...}` ladder. Every section runs through `safeRun` (in `checks.go`), which recovers panics into a `StatusWarn` SectionResult with a `checks.section.panic` finding — so a panic in one check degrades that section to a warning instead of aborting the whole scan. Preserve registry ordering; it determines output section order.
- **Git subprocess hardening contract (threat model: untrusted PR).** `base_ref` from MCP/CLI is validated by `runnersupport.ValidateBaseRef` (rejects leading `-` to block git option injection; restricts charset; preserves the `stdin` sentinel) BEFORE reaching git, and `--end-of-options` is passed to git diff/show/worktree. All git/govulncheck subprocesses use `exec.CommandContext` with a contained timeout and read output through `io.LimitReader` (`maxGitOutputBytes`) to prevent hangs/OOM. The `//nolint:contextcheck` markers in the git layer (`runner/support`, `ai/fix`, `ai/semantic`, `checks/quality/quality.go`, `runner/runner.go`) are DELIBERATE — the contained timeout is the chosen design; threading caller `ctx` end-to-end is a tracked follow-up. Don't "fix" them by removing the nolint without actually threading ctx. `runner/support/MatchPattern` (glob→regex) uses `regexp.Compile` + a `sync.Map` cache and returns false (never panics) on a malformed config glob.
- **The usage menu makes one outbound call (opt-out).** Running `codeguard` with no args or `help` renders a "What's New" banner (`internal/whatsnew` + `internal/cli/whatsnew.go`) that queries the GitHub releases API for the latest version. It is disabled when `CODEGUARD_NO_UPDATE_CHECK` is truthy OR `$CI` is non-empty (so CI/automated runs make no surprise call), caches the result for 24h under `os.UserCacheDir()/codeguard/update-check.json`, uses the SSRF-guarded `ai/safehttp.Client` with a 1.5s timeout, and fails silent (falls back to stale cache, then to version-only). Changelog bullets come from `CHANGELOG.md` embedded via a **module-root package** (`/changelog.go`, `package codeguard`, imported as `root "github.com/devr-tools/codeguard"`) — `go:embed` cannot reference `../CHANGELOG.md`, so the embed directive must live at the repo root, not in `internal/`.
- **Lint is enforced in CI.** `make lint` is `go vet`; `make lint-strict` / the CI `golangci-lint-action` step (now blocking — no `continue-on-error`) runs the 16-linter `.golangci.yml`. `golangci-lint run` must report 0 before pushing. The config excludes revive's documentation/naming style rules (`exported`, `package-comments`, `unused-parameter`) and excludes `tests/` from gosec/errcheck/prealloc/bodyclose (intentional fixtures). Cache/identity keys use sha256 (not sha1). Documenting the public `pkg/codeguard` API with doc comments is a known follow-up (revive `exported` is currently excluded rather than satisfied).
- **Adding a check section touches a fixed wiring list; two are silent-failure traps.** Beyond the obvious (check package with `Run(ctx, env) core.SectionResult`, a `sectionDef` in `runner/checks/registry.go`, a `CheckConfig` bool + rules struct in `core/config_types.go`/`config_rule_types.go`, catalog + fix-template maps merged in `rules/catalog.go`/`catalog_fix_templates.go`, defaults in `config/defaults*.go` + `example*.go`, docs): (1) `runner/support/cache_helpers.go` — add the section to `SectionConfigHashes` AND `sectionConfigFamily`, else the section's per-file cache keys fall back to the all-checks fingerprint (correct but invalidates on any config change); (2) top-level `CheckConfig` bools get NO defaulting in `applyCheckDefaults` — an omitted `checks.<section>` key means **off**, which is how the opt-in `performance` and `supply_chain` sections work. The performance section (v0.9.0) is the reference move: rules migrated from quality with renamed ids (`quality.*` → `performance.*`), no runtime aliasing, `rules.RetiredPerformanceRuleIDs()` powers a `codeguard doctor` waiver migration hint.
- **PERF: the quality AI checks read through the corpus via `checks/support.Context.ListTargetFiles`/`ReadTargetFile`** (wired in `runner/checks/checks.go`, backed by `runnersupport.ListTargetFiles`/`ReadTargetFile`; `checks/quality/quality_ai_corpus.go` holds the nil-safe fallbacks for unit-test contexts). GOTCHA when routing more reads through the corpus: `corpusRead` caps at 32 MiB (`readCappedFile`) while `os.ReadFile` does not — walk-enumerated files are already under the cap so behavior is identical, but fixed-filename reads that never went through the walk (`go.mod`, root `package.json`, python manifests) deliberately stay direct `os.ReadFile` to preserve semantics. The Go repo-dominant style signals (test framework, error style, naming) are computed in ONE corpus pass (`goRepoStyleProfile` in `quality_ai_target_go.go`); each signal is an independent per-file sum, which is what makes the fold behavior-identical.
- **GOTCHA: `goFuncEligibleForUnusedCheck` must not consult `fn.Doc`.** The AI dead-code pass historically parsed with `parser.ParseFile(..., 0)`, so `fn.Doc` was always nil and the "go: directive implies external use" exemption NEVER fired. The pass now reuses the shared ParseComments corpus AST (`support.ParseGoSource`), where `fn.Doc` IS populated — keeping that check would have silently exempted unused functions carrying `//go:generate`-style comments and changed findings. It was removed to keep output identical (see the NOTE in `quality_ai_dead_code.go`); activating it is a candidate behavior fix, to be made deliberately with tests.
- **PERF: clone-detector hashing is not behavior-bearing.** `cloneToken` now stores the original-case source slice plus a per-token FNV-1a hash of the ASCII-lowercased text (tokens are ASCII-only by the regex); window grouping uses a rolling polynomial hash (`cloneWindowIndex`) and equality is verified token-by-token in `sharedCloneLength` (hash short-circuit + ASCII case-fold compare). Because every candidate is value-verified, ANY deterministic hash yields identical clone candidates — collisions only cost time. `tests/checks/quality_clone_differential_test.go` pins findings captured from the pre-rewrite algorithm; don't regenerate its expectations with the current code.

- **Finding identity excludes presentation.** Exact, context, and content fingerprints derive from rule ID, path, line, and source identity only (`runner/support/findings_section.go`) — never message prose, metadata, confidence, or the *reported* level. Confidence demotion (`checks.confidence_demotion`) rewrites `Level`/`Severity` after `NewFinding`, so a demoted finding still matches its baseline entry. Any future policy that changes how a finding is reported must preserve this.
- **Post-cache policy must be stripped from cache fingerprints.** `SectionConfigHashes` calls `findingRelevantChecks` to zero settings that cannot change per-file findings (currently `checks.min_confidence` and `checks.confidence_demotion`), including for the conservative `""` all-checks family. Filtering happens in `FinalizeSectionWithDiagnostics`, i.e. after `cachedFileFindings`, so a threshold change must re-render a scan, never invalidate cached findings. Add any new finalize-time-only setting to that strip list.
- **Section ids diverge between the registry and reports.** `runner/checks/registry.go` uses `supply-chain`, but the section finalizes as `supply_chain`, which is what appears in `SectionResult.ID`, in `checks.disabled`, and in `checks.min_confidence.sections`. `core.SectionKeys()` holds the report-facing list; `tests/codeguard` asserts every id a real scan reports is in it.
- **`config.WriteFile` stamps `codeguard_version`, `ApplyDefaults` does not.** The stamp is applied at the write boundary so a *loaded* config keeps whatever its file recorded — that is what makes it useful for spotting a config produced by another release. It is never validated (any value, including an unparseable one, must still load), and it is absent from `SectionConfigHashes`, so a release upgrade cannot discard cached findings. Release builds write `v{{.Version}}` (GoReleaser `-X internal/version.Number=v{{.Version}}`), so hand-maintained configs use the `v`-prefixed form; a local dirty build writes e.g. `v1.9.0+dirty`.

- **`baseExampleConfig()` (`config/example*.go`) IS the built-in defaults source, not just `init` scaffolding.** `ApplyDefaults` → `defaultConfigForProfile` → `baseExampleConfig()`, then the profile spec overlays it. So every value in `exampleCIRules()`/`examplePromptRules()`/etc. silently becomes the effective default for users who omit that key. Consequence to keep in mind when editing those functions: `AllowedTestPaths: []string{"tests/**"}` makes `ci.test-file-location` (**fail** level) active by default, so a config of just `checks: {ci: true}` hard-fails any repo using co-located `_test.go`, NestJS `.spec.ts`, pytest `test_*.py`, or a `test/` (singular) directory — verified: 109 fail findings on an ordinary Go repo. Same coupling puts `RequiredWorkflowFiles: [".github/workflows/ci.yml"]` and a `RequiredContains: ["go test ./..."]` content rule in every unconfigured scan. Treat a change to `example*.go` as a change to global default policy, and prefer leaving house-style keys empty there (the rule already no-ops on an empty `AllowedTestPaths`).
- **Default excludes are much narrower than they look, and only three are segment-matched.** `shouldExclude` (`runner/support/utils_match.go`) applies glob defaults `.git/**`, `.gocache/**`, `.gomodcache/**`, `.codeguard/**`, `dist/**` plus `isDefaultDependencyOrBuildPath`, which segment-matches only `node_modules`, `cdk.out`, and `vendor`. Because the globs are anchored at the target root, **nested build output is scanned**: `services/app/dist/**` is NOT excluded (only root `dist/`), and `.next/`, `build/`, `out/`, `target/`, `.venv/`, `site-packages/`, `__pycache__/`, `coverage/`, `.terraform/`, `.turbo/`, `*.min.js`, `*.map` are not excluded at all. Measured impact on real repos: 97% of findings on one Next.js monorepo and 78% on another came from `.next/`; a Go repo with a `.build/go-cache` tree produced 566 security findings against compiled cache objects. Note `.gocache` is a default but `.cache/go-build` (the more common name) is not. Any new exclusion belongs in `isDefaultDependencyOrBuildPath` (segment-matched, depth-independent), not in the anchored glob list.
- **CORRECTION to the hardening note above: `looksBinary` is NOT general scanner hardening — it guards only the secrets pass** (`security_secrets.go:105`, its sole caller). Every other line/regex detector (weak-hash, weak-cipher, the per-language shell-execution/dynamic-code/unsafe-html-sink patterns) will happily regex compiled binaries and minified bundles, reporting findings at lines inside object code. If you add a repository-wide line scanner, add the `looksBinary` guard yourself; consider hoisting it into the corpus read path instead.
- **`parseLockfileState`'s bool means "I recognised this format", never "I found packages".** `SupplyChainLockfileIssues` has a `parsedAny` guard so an unparseable lockfile stays silent, but several branches historically hardcoded `true`, which defeated it: a parser that understood nothing reported *every* manifest dependency as drift, and `supply_chain.lockfile-drift` is **fail** level, so one parse bug became a fail per dependency (measured: 33 on a Yarn Berry repo, i.e. its entire `package.json`). A parser that recognised nothing MUST return false. Distinguishing "genuinely empty" from "unparsed" needs positive format evidence, not just a zero count — self-identifying keys (`lockfileVersion`, `importers`, `snapshots`) for the JSON/YAML formats, and for the TOML block formats either a seen `[[package]]` table or an all-lines-are-known-header-keys check, so a merge-mangled file fails on its garbage lines while a dependency-free lock still gets compared.
- **Lockfile package-name comparison is ecosystem-gated on `core.SupplyChainManifest.Ecosystem`, and must stay that way.** Python normalises per PEP 503 (lowercase, runs of `-_.` collapsed to `-`) because `pyproject.toml` records `Jinja2`/`typing_extensions` while `poetry.lock` records `jinja2`/`typing-extensions`. npm must NOT normalise — names are case-sensitive and `_` vs `-` are genuinely different packages, so blanket normalisation creates false negatives (there is a regression test pinning `Left_Pad` vs `left-pad` as real drift). Cargo also stays exact: crates.io treats `-`/`_` as distinct and blocks registering both spellings, and `Cargo.lock`'s `name` is the canonical index name. Go module paths are case-sensitive with `!x` escaping.
- **Yarn has two incompatible lockfile syntaxes and Berry's is the common one now.** Classic v1 writes `version "2.6.0"`; Berry (v2+) writes `version: 2.6.0` unquoted under a `__metadata:` header. Berry selectors also carry a protocol — `@linear/sdk@npm:^2.6.0`, plus `workspace:`, `link:`, `portal:`, `file:`, `patch:`, `git:`/URL — so the package name must be split at the first **non-scope** `@`, not the last (splitting at the last also mis-parsed classic npm aliases like `aliased@npm:real@^1.0.0`). Non-registry protocols are not version ranges and the manifest side is never `Pinned` for them, so record them as present-with-resolved-version and skip the range comparison. `bun.lockb` is listed as a lockfile candidate in `parsePackageJSONManifest` but is a binary format with no parser branch, so bun repos get no drift coverage at all.
- **Exclusion has two layers with deliberately different power, and the asymmetry matters.** `ShouldExclude`/`shouldExclude` is a **pure path predicate**; the corroboration for ambiguous build-output names (`build`, `out`, `bin`, `obj`, `target`, `coverage`, `_build` — skipped only when a sibling manifest such as `Cargo.toml`, `pom.xml`, a `.csproj`, `CMakeLists.txt` or `build.gradle` proves the directory is that build system's output) needs the filesystem, so it lives in `walkFilesBounded` via `isCorroboratedBuildOutputDir`. Consequence: those names are pruned during a repository walk but are NOT reported as excluded by `ShouldExclude`, so a path-only caller (e.g. diff-mode filtering) still sees them. The asymmetry errs toward scanning, which is the safe direction — but any new path-only exclusion caller needs to know it exists. Python markers are intentionally absent from `coverage`'s marker list because coverage.py's own repo has a `coverage/` *source* package next to its `pyproject.toml`; `package.json` is intentionally absent from `build`'s, because JS repos keep build *scripts* there.
- **`exclude` entries support a leading `!` as a re-include that overrides the built-in defaults** (e.g. `exclude: ["!packages/ui/dist/**"]`). This is the only escape hatch for the unconditional defaults, notably `dist` and `venv` (CPython's stdlib really does have a `Lib/venv/` source package). It required a second mechanism: directory pruning is suppressed when a re-include *could* match inside the directory (`reincludeMayCoverSubtree`), else the walk prunes the parent before the negation can apply — the same problem gitignore negation has. `reincludeMayCoverSubtree` is deliberately loose: a re-include whose glob starts with a wildcard (`!**/dist/src/**`) disables ALL directory pruning, which is a walk-cost cliff, not a correctness one (files inside stay excluded individually). Note this was added under a scope constraint rather than designed as config API — a `core.Config` flag would be the cleaner long-term shape.
- **`dirHasEntryWithSuffix` is deliberately not memoized**: codeguard also runs as a long-lived MCP server, where a cached directory listing would serve a stale answer across scans.
- **Narrow default exclusions caused false NEGATIVES, not just false positives.** Before build output was excluded depth-independently, a Next.js monorepo's `.next/` tree exhausted the shared corpus budget: the scan emitted `scan.corpus-budget` ("remaining uncached work was skipped") and `quality.duplicate-code-budget`, and real-source findings were *suppressed* — one repo went from 255 real-source findings to 665 once `.next` was excluded, with both budget diagnostics disappearing. So a flood of generated files silently starves analysis of real code. When triaging "why didn't codeguard flag X", check the section diagnostics for budget exhaustion before assuming a detector gap.
- **Credential fixture classification is two orthogonal axes, and the asymmetry is the security property.** `classifyPathScope` (`security_fixture_demote.go`) yields `non_fixture`/`fixture`/`documentation` from path evidence and can only ever **demote** (fail/high → warn/medium, message annotated); suppression to an info diagnostic requires evidence about the **value** (vendor-documented placeholder, filler marker, unroutable host). Rationale: a path is attacker-choosable and a real key in a `_test.go` is still a leaked key. Consequence for contributors: adding a path convention cannot create a detection bypass, but adding a value signal can — so keep value signals exact. `private_key` and `high_entropy` matches are never path-demoted at all, and `security_rules.demote_fixture_findings: false` restores strict fail/high for everything (verified). The git-history scan is deliberately unaffected (it goes through `Scanner.ScanContent`, not `secretResultsForFile`) because anything ever committed must be rotated regardless of where it lived.
- **`isPlaceholderSecret` only suppresses "example"-ish values for patterns that have a capture group.** The AWS/GitHub/Slack/Stripe provider patterns have none — the whole match is the token — which is why AWS's own published `AKIAIOSFODNN7EXAMPLE` used to fire at fail/high on any path. Vendor-documented placeholders are now an explicit exact-literal denylist applied path-independently. Check this behaviour whenever adding a new provider pattern.
- **`security_rules.demote_fixture_findings` is live again**; `core/config_rule_types.go:276` still describes it as "retained for configuration compatibility", which is now stale and should be corrected.
- **UPDATE to the `baseExampleConfig()` bullet above (branch `fp/defaults-vs-example-config`): the two roles are now split.** `ApplyDefaults` resolves omitted keys against `baseDefaultConfig()` (`config/defaults_base*.go`) — scan mechanics, off-or-scan-mode section activation, and thresholds with no meaningful unset value. `baseExampleConfig()` (`config/example.go`) is that baseline plus `applyStarterPolicy()` — targets, the recommended section set, and codeguard's own CI/layering conventions — and is what `codeguard init` writes. Rule for contributors: anything added to the baseline is policy enforced on every user, so repository-shape policy (filenames, content markers, test layout, package layering) belongs in the starter or a profile. Two adjacent traps: (a) a `def`-supplied value is only actually a default if some `apply*Defaults` function reads it — many `Detect*` booleans are hardcoded `true` and ignore `def` entirely, and roughly a third of the old example config was inert on the defaults path; (b) `applyCIDefaults`/`applyDesignDefaults` used to hardcode `boolPtr(true)` for `require_workflow_dir` and the four layering toggles, so editing the constructor had no effect — they now read from the baseline.
- **STILL OPEN: the config-less `scan -folder` path bypasses `ApplyDefaults` entirely.** `internal/cli/helpers.go:81 exampleConfigForProfile` returns `service.ExampleConfig()` / `ExampleConfigForProfile()` — the *starter*, not the baseline. Verified: a config-less folder scan of an ordinary Go repo still produces 144 fail-level findings (109 `ci.test-file-location`, 6 `design.service-import-internal`, 5 `ci.workflow-content`) even with the defaults split in place. This is the zero-config first-run experience, and `docs/getting-started.md:53` advertises it as "CodeGuard's built-in default config", which is now the wrong term. Fix is for that path to build from the baseline plus the recommended section set.
- **`design.cmd-through-internal-cli` cannot fire outside this repository.** `checks/design/design_go.go:141` requires `strings.Contains(pathValue, "/pkg/codeguard")`. Verified. It shipped as a fail-level default that is a guaranteed no-op for every other user.
- **`design_rules.forbid_internal_import_cmd` is dead config.** Verified: it appears only in `core/config_rule_types.go:220`, `config/defaults_rules.go:100`, the example config, and `docs/checks.md:1547`. No check reads it — it is validated, documented, defaulted, and inert.
- **A `profile:` set inside a config file cannot enable the plain-bool check sections.** `applyCheckDefaults` only defaults the `*bool` sections from `def`, so `ai-safe`'s `Prompts`/`Security` and `enterprise`'s `SupplyChain` are inert when the profile arrives via config; they only take effect through `ExampleConfigForProfile` (i.e. `init --profile`). Pre-existing, and it means `enterprise` is quietly weaker on the defaults path than its description.
- **`isPluralName` (`quality_precision_workstreams_cd.go`) returned `false` for every possible input, so half of `naming.cardinality-mismatch` had never fired.** `unitSuffixPattern` lists a bare `s` among its `$`-anchored alternatives (intended for "seconds"), so any `s`-ending name looked unit-suffixed and returned false, while any non-`s` name failed the `HasSuffix(name, "s")` test — both branches false, unconditionally. Every one of the 586 measured findings came from the rule's *other* half. Two related smells in the same file: `conventionalCardinalityName` is a ~120-entry literal allowlist harvested from one codebase (`atrisk`, `krs`, `requestsbypillar`, `latestquarter`, `prisma`) — the signature of a predicate patched by pasting in names instead of being fixed — and `collectionTypePattern` is unanchored on `record|set|list`, so `EventRecorder`, `Offset` and `Listener` all read as collection types.
- **The honest confidence line for the `defensive.*` family is analysis mechanism, not rule family.** Its two AST-driven members (`unchecked-type-assertion`, `unsafe-numeric-conversion` — real `*ast.TypeAssertExpr` + comma-ok analysis) earn `high`; the ~11 regex-over-lowercased-function-body members do not. Two rules rated `high` were measured at 100% FP with structural causes: `fail-open-authorization` matched `err != nil { … return nil }` gated only on the body mentioning "auth"/"policy" — i.e. every Go function that mentions policy and uses the fail-*closed* idiom — and `unsafe-default` chained three `.*?` segments off the bare substring `config` with unbounded safety tokens, so `ConfigFields: []string{...}` and `gitSkippableFlag` ("skip" inside "Skippable") matched. Both are now `medium`/`low`. Nine regex members still carry `medium` on no measurement; treat that as unverified.
- **`quality.dependency-direction` duplicates a compiler-enforced invariant and is recommended for retirement.** Go already rejects importing another module's (or another subtree's) `internal/`, including the monorepo `services/a` → `services/b/internal/x` case, while same-module internal imports from `cmd/`, `pkg/` or an external test package are legal and idiomatic — which is why the old exemption had to hardcode `pkg/codeguard/` via `IsSDKFacadeFile`, flagging every *other* repo's `pkg/<name>/` facade. All 631 measured findings were legal same-module imports; expected true-positive yield is ~0 for any buildable single-module repo. Its catalog entry also described behaviour ("non-CLI packages import CLI-only implementation details") the implementation never had. Properly-scoped successor: `design.service-import-internal`. Retirement precedent: `rules.RetiredPerformanceRuleIDs()` + a `codeguard doctor` waiver-migration hint.
- **`defensive.bounds-assumption` fires inside generated `proto/**/*.pb.go`.** Generated-source exclusion for the `defensive.*`/precision families is a separate gap from the `.next/`/`dist/` walk exclusions — those rules run on files the walk legitimately includes.
- **`IsSDKFacadeFile` hardcodes `pkg/codeguard/`, so codeguard exempts itself from fail-level rules it applies to everyone else.** `runner/support/utils_match.go:29` is `strings.HasPrefix(normalized, "pkg/codeguard/")`. It is the exemption consumed by `design.service-import-internal` (**fail**), `design.service-import-cmd` (**fail**), `quality.dependency-direction`, and `change.unnecessary-surface-area`. **Verified with two fixtures identical but for the directory name**, both doing the legal, idiomatic same-module `pkg/<name>` → `internal/` import: `pkg/myapp` → `design.service-import-internal` (fail) + `quality.dependency-direction` (warn); `pkg/codeguard` → zero findings. This is a guaranteed fail-level false positive on every repository except this one. The fix is to make the facade path configurable (e.g. "any single directory directly under `pkg/`"). `fp/quality-rule-precision` fixes only the `quality.dependency-direction` half; the two `design.*` fail rules are unfixed on every branch. Sibling case: `design.cmd-through-internal-cli` (`checks/design/design_go.go:141`) requires `/pkg/codeguard` in the *imported* path, so it is the inverse — it can only ever fire inside this repo.
- **Five emitted performance rule IDs are absent from the catalog, so `codeguard explain` fails for findings the tool just printed.** Verified: `performance.go.nested-loop-scan`, `performance.go.slice-membership-in-loop`, `performance.go.lock-held-across-blocking-call`, `performance.cpp.range-for-copy`, `performance.cpp.flush-in-loop` all return `unknown rule "..."`. They are documented in `docs/checks.md` and carry weights in `performance_score.go` — only `rules/catalog_performance.go` is missing them. Consequence: no metadata, no fix template, no OWASP mapping, no SARIF rule descriptor. Catalog→implementation is clean (360/360); it is the **reverse** direction that has no enforcement. Add a test asserting every rule ID emitted under `checks/**` resolves in `rules.Catalog()`.
- **CORRECTION: codeguard DOES have an inline suppression directive** — `codeguard:ignore <rule> [until YYYY-MM-DD]`, `runner/support/suppressions.go:19`, documented at `docs/checks.md:2150`, counted as `InlineSuppressed` in rule-stats. **But prefix globs silently do nothing.** The regex ruleID class is `[a-z0-9._*\-]+` so `codeguard:ignore security.*` parses cleanly, while the match at `suppressions.go:132` is `directive.ruleID != "*" && directive.ruleID != finding.RuleID` — exact match or bare `*` only. Verified: an exact rule id suppresses, a bare `*` suppresses, and `security.*` leaves the finding reported with no warning. Either support prefix globs or reject them at parse time. Also note `MatchSuppression` is called per finding and does an uncached `os.Stat` + `os.ReadFile` + full-file split + per-line regex, so a 23k-finding scan re-reads files 23k times.
- **`checks.disabled` accepts section names only — there is no per-rule disable.** The only way to turn off a single bad rule is `waivers: [{rule: X, path: "**"}]`, which routes a permanent policy decision through the temporary-exception mechanism: it inflates `suppression_ratio`, which is the very metric `doctor_rule_health.go` uses to judge rule health, and it surfaces in the waiver audit as something to review. Every comparable tool (Semgrep `--exclude-rule`, Ruff `lint.ignore`, staticcheck `-SA9003`, golangci-lint `linters.disable`, ESLint per-rule severity) has per-rule disable.
- **A corpus budget miss must never become a work skip.** The original design, on exceeding `maxCorpusReadBytes`/`maxCorpusGoASTSourceBytes`, returned an error instead of the content — and `VisitTargetFiles` (`runner/support/artifacts.go:65`) `continue`s on any read error. So an over-budget scan silently *skipped files* rather than merely failing to cache them: with a starved budget a 40-file target visited 2 files. Cross-file passes (clone detection, import graphs, agent-context inventory) were fed a truncated stream whose truncation point was a scheduling race, because concurrent sections share one corpus. The fix is to serve over-budget work **uncached** — read and return the bytes, parse without retaining — which leaves retention bounded exactly as before while removing the skip. What the old design actually bought was not memory safety but a crude throttle on total work, paid for in silently missing findings; work bounds belong in explicit reported limits (`maxScanFileCount`, `maxScanFileBytes`), not in a cache.
- **The Go AST budget counted source bytes while retaining trees — it was ~9× off.** A retained `ParseComments` AST plus FileSet measures 8.4–9.0× its source bytes, so `maxCorpusGoASTSourceBytes = 64 << 20` admitted roughly **576 MiB of live AST**, not 64 MiB. Express such budgets in retained bytes with the expansion factor applied. Related bug in the same area: once the byte budget latched `readExhausted`, every later miss re-recorded as `read_entries`, so a scan reported "50,000-entry limit reached" after caching 3,824 files.
- **For TypeScript targets the dominant memory consumer is a child process, not the corpus.** `checks/support/typescript_semantic.go:89` spawns `node -e <embedded runner>`; measured on one repo, codeguard itself peaked at 74 MiB while the total including the child was 1.28 GiB. No corpus budget touches this. Peak RSS otherwise tracks corpus *retention*, not repo size (`selfRSS ≈ 35 MiB + ~1.3× retained bytes`) — the largest repo measured had the smallest Go heap.
- **Several direct reads bypass the corpus with no size cap at all** (not even `readCappedFile`'s 32 MiB), while reading walk/diff-derived repository content: `checks/contracts/contracts.go:65` (`readHead`, paths from the PR diff — attacker-influenced under the stated threat model), `checks/quality/quality_precision_delta.go:72`, `quality_python_toolchain_dead_code.go:161`, `quality_cpp_toolchain_dead_code.go:420`, `checks/support/supply_chain_licenses_resolution.go:41,57`. Manifest/lockfile/config reads bypassing the corpus are deliberate and fine; these are not.
- **Warn/fail diagnostics were invisible in the text report.** Only JSON/SARIF carried them, so "walk stopped early" and `scan.govulncheck.*` failures never reached a terminal reader. If you add an operational diagnostic, check it actually renders in the format the user is looking at.
- **Map iteration + an early exit is a findings-nondeterminism bug class in this codebase; two confirmed instances.** Go randomizes map iteration order, so any `for ... range someMap` whose body `break`s at a cap or `return`s a result makes the output depend on scheduling. (1) `collectCloneCandidates` (`quality_clone.go`) walked the `cloneIndex` map and stopped at `maxClonePairComparisons`/`maxCloneCandidates` — the order decided *which* window hashes were examined before the cap, and `sortCloneCandidates` orders the result but cannot recover what was never collected. Proven: a 120-file synthetic repo saturating the cap gave three distinct finding sets over five runs, all capped at the same count. (2) `dataClumpFindings` (`quality_smells.go`) returned the first qualifying parameter group straight out of a map range, so a file with several qualifying groups reported a different group/line/message per run, sometimes a weaker clump than one already passed over. Both now iterate deterministically (sorted hash keys; worst-clump-then-key). A sweep of `checks/**` for the same shape found seven more candidates, all verified benign — they are existence checks returning a bool, where any match gives the same answer. **When adding a capped or first-match scan, iterate a sorted key slice, not the map.**
- **`appendCommonLineFindings` runs on every line of every NON-Go file.** `goParsed` is false for all non-Go files, so the two "Go-oriented" fallback patterns scanned every YAML, JSON, Markdown and minified JS line in the tree. The function name actively misleads; check the gate condition before assuming a language-named helper is language-scoped.
- **`builtinGatePasses` has a pre-existing latent false negative the newer per-line gates do not.** It has no non-ASCII bail-out, so a line containing `ſecret` (U+017F) is rejected by the gate even though `(?i)secret` would match it — Go's `(?i)` folds `s`→U+017F and `k`→U+212A. The per-line `gatedPattern` gates always pass on non-ASCII input for exactly this reason. Fixing `builtinGatePasses` is a one-liner but it can only *add* findings, so it is a behaviour change to make deliberately with tests, not bundled into perf work.
- **The facade exemption is asymmetric by rule, deliberately.** `design.service-import-internal` is exempted inside the resolved SDK facade; `design.service-import-cmd` has no exemption at all, because a public package importing `cmd/` is a layering inversion under any layout. Since the default heuristic treats *every* directory under `pkg/` as a facade, re-unifying the early return would silently retire both fail rules for most repositories.
- **`make([]T, 0, N)` with N > 0 allocates; `make([]T, 0)` does not** (it returns `zerobase`). A per-line helper returning `make([]core.Finding, 0, 3)` cost ~1 GB per scan pass. Return `nil` or a zero-capacity slice from hot helpers that usually find nothing.
